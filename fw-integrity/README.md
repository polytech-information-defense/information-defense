# fw-integrity — подсистема контроля целостности ПО МЭ

Подсистема реализует требования ЦЛС-01 – ЦЛС-07 и проверку состояния ОС из
ОБР-02. Написана на Python 3.13, сторонних зависимостей нет: используется
только стандартная библиотека.

## Что делает

| Требование | Где реализовано |
|---|---|
| ЦЛС-01: SHA-256 исполняемых и конфигурационных файлов | `manifest.py` (что проверять), `checker.py` (как) |
| ЦЛС-02: эталоны при установке и при легитимных изменениях | `fw-integrity init`; команды `begin_update` / `commit_update` |
| ЦЛС-03: при запуске, каждые 1–1440 мин (по умолчанию 10), по запросу | `IntegrityService.startup`, `daemon.periodic_checks`, команда `integrity_check` |
| ЦЛС-04: блокировка трафика, событие с перечнем файлов, аварийный режим | `service._enter_emergency`, `actions.SystemTrafficControl.block` |
| ЦЛС-05: перечень нарушений, восстановление из копии, повторная проверка | команды `list_violations`, `restore`, `integrity_check` |
| ЦЛС-06: автоматическое возобновление после успешной повторной проверки | `service._leave_emergency` |
| ЦЛС-07: нарушение при запуске — сразу аварийный режим | проверка до `READY=1` + `fw-integrity gate` в юните fw-filter |
| ОБР-02: расхождение настроек ОС = нарушение целостности | `os_state.py` |
| События 106, 416, 500–505 | `events.py`, коды в `constants.py` |
| АПИ-03, АПИ-04, АПИ-09: JSON-строки, коды ошибок | `protocol.py` |

## Структура

```
fw_integrity/
  constants.py   коды событий и ошибок, режимы, роли
  config.py      настройки процесса (/etc/fw/integrity.json)
  manifest.py    перечень контролируемых файлов (шаблоны * и **)
  hashing.py     SHA-256 файла
  store.py       эталоны, резервные копии, карантин, файл состояния
  checker.py     сравнение файлов с эталонами
  os_state.py    проверка настроек ОС по таблице ОБР-02
  protocol.py    сервер и клиент JSON-строк через UNIX-сокет
  events.py      отправка событий в подсистему регистрации (с очередью)
  actions.py     глобальная блокировка трафика и её снятие
  service.py     логика подсистемы: команды API, аварийный режим
  daemon.py      процесс: сокет, проверка при запуске, периодическая проверка
  client.py      помощники для других подсистем (legit_update)
  cli.py         командная строка
tests/           65 тестов (unittest)
packaging/       юнит systemd, drop-in gate, настройки, пример манифеста
docs/            схема подсистемы (draw.io) и её описание (LaTeX)
```

## Как это работает

**Два вида файлов.** Манифест делит контролируемые файлы на два вида:
- `static` — код и неизменяемые файлы. Меняются только при установке
  ПО МЭ, эталоны для них формирует `fw-integrity init`.
- `config` — конфигурационные файлы, которые подсистемы меняют в работе:
  сохранённая конфигурация, политика, учётные записи.

**Хранилище** находится в `/var/lib/fw/integrity/`, доступ только у root:
- `reference.json` — эталоны: путь → SHA-256, вид, размер, права;
- `backup/<sha256>` — резервные копии. Копия делается при том же чтении
  файла, что и хеш, поэтому эталон всегда совпадает с копией;
- `quarantine/` — посторонние файлы, убранные при восстановлении;
- `state.json` — режим (`normal` или `emergency`), нарушения, период,
  последняя проверка, идентификатор загрузки.

**Проверка.** Каждый файл с эталоном хешируется и сравнивается с ним.
Кроме того, по шаблонам манифеста ищутся посторонние файлы, в том числе
скрытые: подброшенный `.evil.py` тоже будет найден. Если включено
`os_check`, сверяются настройки ОС. Нарушение — это любой из случаев:
файл изменён, удалён, добавлен или не читается, либо настройка ОС не
совпадает с ОБР-02. Отсутствие эталонов или повреждённый манифест тоже
считаются нарушением: то, что невозможно проверить, считается небезопасным.

**Аварийный режим** (ЦЛС-04) включается так:
1. Режим записывается в `state.json`. С этого момента `gate` не пустит
   перезапуск fw-filter.
2. Подсистеме фильтрации отправляется `set_emergency {"enabled": true}`:
   она сразу начинает удалять все кадры.
3. Останавливаются службы из `emergency_stop_units` (по умолчанию
   fw-filter, fw-web, ssh). Даже после остановки fw-filter трафик не
   идёт: правило `drop` на `netdev ingress` (ОБР-02) остаётся в силе. В
   аварийном режиме доступен только локальный CLI (ЦЛС-05).
4. Регистрируются события 501 (со списком файлов) и 502.

**Выход из аварийного режима** (ЦЛС-06). После восстановления
администратор запускает повторную проверку. Если она успешна, службы
запускаются, фильтрации отправляется `set_emergency {"enabled": false}`,
регистрируется событие 504. Периодическая проверка в аварийном режиме тоже
продолжается: если файлы восстановлены, работа возобновится и без
отдельной команды. Пока нарушения те же, событие 501 повторно не пишется.

## API (сокет `/run/fw/integrity.sock`)

Формат: одна JSON-строка на запрос и на ответ. Поле `ctx` описывает, кто
вызывает команду:
- администратор: `{"user": "ivanov", "role": "rw" | "ro", "iface": "console" | "ssh" | "web", "ip": "10.0.0.5"}`;
- подсистема: `{"subsystem": "filter"}`.

| Команда | Параметры | Кто может | Что делает |
|---|---|---|---|
| `get_status` | — | ТЧ, ЧЗ, подсистема | режим, последняя проверка, период, время до следующей проверки |
| `integrity_check` | — | ТЧ, ЧЗ, подсистема | проверка по запросу (функция 29) |
| `list_violations` | — | ТЧ, ЧЗ, подсистема | перечень нарушений (ЦЛС-05) |
| `get_params` | — | ТЧ, ЧЗ, подсистема | `{"period_min": 10}` |
| `set_params` | `period_min`: 1…1440 | ЧЗ, подсистема | изменить период (функция 30), событие 416 |
| `restore` | `path` или `all: true` | только ЧЗ | восстановить из копии / убрать в карантин, событие 503 |
| `begin_update` | `path` | подсистема | начать легитимное изменение файла `config` |
| `commit_update` | `path` | подсистема | обновить эталон и копию, событие 505 |
| `abort_update` | `path` | подсистема | отменить изменение |

Пример:
```json
{"id": 1, "command": "set_params", "params": {"period_min": 30}, "ctx": {"user": "ivanov", "role": "rw", "iface": "web", "ip": "10.0.0.5"}}
{"id": 1, "status": "ok", "result": {"period_min": 30}}
```
Коды ошибок: `bad_request`, `unknown_command`, `invalid_params`,
`not_found`, `forbidden`, `invalid_state`, `internal`. Отказ по правам
дополнительно регистрируется событием 106.

## Что нужно от других команд

**Подсистема фильтрации:**
- реализовать команду `set_emergency {"enabled": bool}`: при `true`
  удалять все кадры, это первый шаг в ОБР-09;
- политику записывать через `legit_update` (см. ниже).

**Подсистема регистрации** должна принимать команду `log_event`
с параметрами:
```json
{"time": "...", "code": 501, "description": "...", "success": false,
 "subsystem": "integrity", "user": "ivanov", "ip": "10.0.0.5", "iface": "web",
 "details": {"files": ["..."]}}
```
Поля `user`, `ip` и `iface` присутствуют, если действие выполнил
администратор. Пока регистрация недоступна, события копятся в очереди
(до 1000) и пишутся в journald.

**Все, кто пишет конфигурационные файлы** (сохранённая конфигурация,
политика, учётные записи), оборачивают запись так:
```python
from fw_integrity.client import legit_update, atomic_write

with legit_update("/var/lib/fw/policy.json", subsystem="filter"):
    atomic_write("/var/lib/fw/policy.json", data)
```
Запись без `begin_update` / `commit_update` будет сочтена нарушением
и включит аварийный режим. Файл пишется атомарно: временный файл, затем
`rename`. Учётные записи лучше хранить в JSON-файле, а не в SQLite в
режиме WAL: файлы `-wal` и `-shm` меняются постоянно.

**Подсистема управления (CLI и web)** вызывает `integrity_check`,
`set_params`, `list_violations`, `restore`, передавая `ctx` администратора.
В аварийном режиме локальный CLI показывает функции ЦЛС-05: нарушения,
восстановление, повторную проверку, журнал, выключение и перезагрузку.

**Системный модуль.** Когда он начнёт настраивать ОС по ОБР-02, включите
`os_check.enabled` и укажите реальные имена портов и TAP-интерфейсов.

## Установка (Debian 13, Python 3.13)

```bash
groupadd --system fwapi
install -d /usr/lib/fw && cp -r fw_integrity /usr/lib/fw/
python3 -m compileall -q /usr/lib/fw                 # байткод собирается сразу и тоже контролируется
install -D -m 0644 packaging/integrity.json /etc/fw/integrity.json
install -D -m 0644 packaging/manifest.json /etc/fw/integrity/manifest.json
install -m 0644 packaging/fw-tmpfiles.conf /etc/tmpfiles.d/fw.conf
install -m 0644 packaging/fw-integrity.service /etc/systemd/system/
install -D -m 0644 packaging/integrity-gate.conf /etc/systemd/system/fw-filter.service.d/integrity-gate.conf
install -D -m 0644 packaging/integrity-gate.conf /etc/systemd/system/fw-web.service.d/integrity-gate.conf
systemd-tmpfiles --create /etc/tmpfiles.d/fw.conf
# после установки ВСЕХ подсистем ПО МЭ:
PYTHONPATH=/usr/lib/fw python3 -m fw_integrity init
systemctl daemon-reload && systemctl enable --now fw-integrity
```
После обновления ПО МЭ: `systemctl stop fw-integrity`, затем
`fw-integrity init --force`, затем `systemctl start fw-integrity`.

Почему каталог `__pycache__` не исключён из контроля: Python выполняет
`.pyc` вместо `.py`, если совпадают время и размер исходника. Подменённый
`.pyc` позволил бы выполнить чужой код, не трогая `.py`. Поэтому байткод
собирается при установке, контролируется вместе с кодом, а службы
запускаются с `PYTHONDONTWRITEBYTECODE=1`.

## Тесты

```bash
PYTHONPATH=. python3 -m unittest discover -s tests
```
65 тестов покрывают:
- проверку и все виды нарушений;
- вход в аварийный режим и выход из него, в том числе при запуске;
- восстановление и карантин, повреждённую резервную копию;
- легитимные изменения и истечение тайм-аута;
- параметры и права доступа;
- протокол и доставку событий;
- блокировку трафика и все пункты таблицы ОБР-02;
- периодическую проверку и командную строку.

Для отладки при запущенном процессе есть команды
`fw-integrity status | check | violations | restore --all | set-period N`.

## Ограничения базовой версии

- `reference.json` защищён только правами root. Злоумышленник с правами
  root может пересчитать эталоны. Усиление: подпись эталонов HMAC-ключом,
  который хранится вне изделия или вводится при загрузке.
- Интерпретатор Python и системные библиотеки не контролируются: это часть
  ОС, а не ПО МЭ. При необходимости `/usr/bin/python3.13` можно добавить
  в `static`.
- Вход администратора в аварийном режиме (ЦЛС-05) выполняет подсистема
  управления. Если повреждена сама база учётных записей, её сначала нужно
  восстановить командой `fw-integrity restore` с консоли от root.
